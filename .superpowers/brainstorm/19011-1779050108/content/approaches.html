3 Architecture Approaches

How should the bot scan 10 coins, generate charts, and send Discord alerts?

A

Async Multi-Coin Scanner Recommended

Bot scans all 10 coins in parallel using async tasks. Each coin runs its own MTF fetch → Fib analysis → signal check cycle. On signal: generate chart with mplfinance, POST to Discord webhook, then paper-trade. Sequential would take 10× longer per cycle.

Pros

  • All 10 coins analysed per 5m candle
  • No coin starves waiting for others
  • Clean, modular — one CoinScanner class per coin

Cons

  • More complex than sequential
  • Binance rate limits need care (handled by ccxt)
B

Sequential Scanner (Simple Loop)

Bot loops through coins one by one: fetch → analyse → signal? → alert → next coin. Simpler to reason about, easier to debug. With 10 coins and ~1s per fetch, one full cycle ≈ 10–15s, well within the 5m window.

Pros

  • Dead simple, no concurrency bugs
  • Easy to add debug logging per coin

Cons

  • Slower (but still fast enough)
  • One slow API call delays all downstream coins
C

Separate Processes per Coin

Each coin runs as its own independent process with its own bot loop. True isolation — a crash on HYPE doesn't affect BTC. Overkill for 10 coins on a laptop but production-grade.

Pros

  • Full fault isolation
  • Easy to add/remove coins independently

Cons

  • 10× resource usage
  • Complex process management
  • Much harder to build & debug
All 3 approaches share the same stack:
• ccxt library → Binance public API for crypto OHLCV (replaces yfinance)
• mplfinance → chart image generation (candlestick + Fib levels drawn on it)
• Discord webhook → POST embed + chart image on signal
• Same DuckDB + FastAPI + React architecture preserved
• No market hours check — 24/7
